Data Formats
============

ReconGraph relies on two primary data inputs: forensic log timelines and Sigma detection rules.

Forensic Log Timeline
---------------------

The primary input for ReconGraph is a CSV file generated by **Plaso (log2timeline)**. 

Required Columns
^^^^^^^^^^^^^^^^

While the tool attempts to be flexible, it specifically looks for the following information:

*   **Message/Description**: The raw log message or event description (often found in the ``message`` or ``desc`` column of a Plaso CSV).
*   **Timestamp**: The date and time of the event (``datetime`` or ``timestamp`` column).

Other formats supported:
^^^^^^^^^^^^^^^^^^^^^^^^

**Plaso JSON Lines** (``psort -o json_line``, ``.jsonl``) are recommended for Windows event logs: the EVTX XML in
``xml_string`` is parsed into named fields (``EventID``, ``Channel``, ``Provider_Name``, every ``EventData``/``UserData``
field), and the Sigma logsource is derived from ``Channel`` and ``EventID``. Only the ``Creation Time`` row of each
record is kept (``--keep-all-timestamps`` keeps all), timestamps before 1970 are dropped, and rows are sorted by time.
``Channel`` holds the ``UserData`` channel when present (e.g. the cleared log of EventID 104), while the logsource
always follows the ``System`` channel. ``Data`` elements without a ``Name`` become ``param1``, ``param2``, ... and are
also joined with newlines into ``Data``. XML-illegal control characters are removed before parsing.

A **Linux audit log** in Plaso JSON Lines (``selinux:line``) gets the logsource tokens ``linux`` and ``auditd``. Each
audit event is one row (see *Event Identity* below), and its ``audit_records`` column holds, as a JSON list, every
record by auditd field names: ``type``, the fields of the record text (those inside ``msg='...'`` included, the outer
field winning on a name clash), ``SYSCALL`` (the syscall name, taken from Plaso's ``system_call``) and the record's
``message``. Text fields (EXECVE arguments ``aN``, ``proctitle``, ``cmd``, ``comm``, ``exe``, ``cwd``, ``name``,
``key``, ``acct``) lose their quotes or are hex-decoded, and ``(null)`` leaves the field out; the ``aN`` of SYSCALL
records are numbers and stay as written. Sigma rules are matched against each record on its own, with the record's
``message`` as the text for keyword selections, and the event gets the rules of all its records; a rule therefore
never combines fields of two records (``a0`` of SYSCALL and ``a0`` of EXECVE).

If not using a Plaso CSV, ReconGraph can also process **raw text logs**. In this case, the tool will treat each line as a description and use the current filename as the source.

Event Identity (``--node=drain``)
---------------------------------

Every row gets an ``event_key``, which is its node in the graph.

.. list-table::
   :header-rows: 1
   :widths: 30 35 35

   * - Row
     - Identity
     - Example
   * - EVTX (``parser`` is ``winevtx``)
     - ``Provider_Name:EventID``
     - ``Microsoft-Windows-Sysmon:1``
   * - Structured artefact (any other ``data_type``)
     - ``data_type:timestamp_desc``, or ``data_type`` for a row without ``timestamp_desc``
     - ``fs:stat:Last Access Time``, ``syslog:ssh:login:Content Modification Time``
   * - Linux audit event (``selinux:line``)
     - ``auditd:audit_type``, followed by ``:system_call`` when the event has a SYSCALL record
     - ``auditd:SYSCALL:execve``, ``auditd:LOGIN:write``, ``auditd:USER_CMD``
   * - Free text (``syslog:line``, ``systemd:journal``, ``android:logcat``, ``ios:lockdownd_log:entry``, ``ios:sysdiag_log:entry``, ``ios:sysdiagnose:logd:line``)
     - ``data_type:template``
     - ``syslog:line:Server listening on <IP> port <NUM>.``

*   **EVTX fallback**: an event with unparsable XML takes its identity from Plaso's ``message``: ``Source Name``, then
    ``Provider identifier``, then ``Channel``, then ``unknown``; likewise the event ID.
*   **Unlisted data types** are structured: one node per data type and timestamp meaning, which never merges two data
    types. The key depends only on the row, so the same event gets the same key in every input. A log format that needs
    templates is one entry in ``recongraph.event_identity.FREE_TEXT_DATA_TYPES``.
*   **Linux audit log** (``audit.log``, Plaso ``data_type`` ``selinux:line``): the records of one audit event (same file,
    timestamp and ``audit_serial``) are one row, put back in the order auditd wrote them, which psort does not keep: the
    record that triggered the event (``CONFIG_CHANGE``, ``LOGIN``, ...), then SYSCALL, BPRM_FCAPS, EXECVE, SOCKADDR, CWD,
    PATH by item number, and PROCTITLE. ``audit_type`` and the other columns come from the first record that has them;
    ``message`` and ``message_body`` join the records' values with newlines. Rows with one timestamp follow the serial
    number. ``timestamp_desc`` is left out of the key because it is the same for every audit event. Other subtyped data
    types are one entry in ``recongraph.event_identity.SUBTYPE_KEYS``.
*   **Plaso CSV** has no ``data_type`` or XML fields. EVTX rows use ``Source Name:EventID`` from ``message``, without
    Drain3. Other rows use ``parser`` in place of ``data_type``, and ``text/*`` parsers count as free text, on ``message``.
    CSV keeps two rows per EVTX record (creation and written time) and all rows are mapped.
*   **Raw text logs** are free text, with the source ``text``.

Drain3 runs with one template miner per data type, on the raw line (``message_body``, ``body``, otherwise ``message``),
with GUIDs, SIDs, hex values, IPs, paths and numbers masked, and in two stages: all rows train the miner, then each row is
matched against the final templates. Configuration and snapshots are in ``recongraph_meta.json``.

This file also lists under ``event_sources`` how each source was treated (``evtx``, ``structured``, ``free_text``), with its
row count, for example ``{"structured": {"syslog:ssh:login": 2}, "free_text": {"syslog:line": 2}}``. The source is the
``data_type``, or ``parser`` for Plaso CSV and ``text`` for raw text logs. It is empty with ``--node=sigma``.

Sigma Annotation
----------------

Sigma runs on every raw row in both node modes. With ``--node=drain`` the result stays an annotation:

*   **Rows**: ``sigma``, ``sigma_all``, ``event_key``, and the level as ``level`` in ``--export-events`` and as ``sigma_level``
    in ``--export-sigma``, where the input can have a ``level`` column of its own.
*   **Nodes**: ``event_key``, ``row_count``, ``sigma_hits`` (rows with an annotation), ``sigma_rules`` (unique, sorted,
    separated by a vertical bar), ``sigma_max_level``. A node can mix annotated and other rows. ``level`` is absent.
*   **Temporal edges**: ``src_level``, ``dst_level``, the level of the two rows.

With ``--node=sigma`` nodes keep ``level`` and have none of the other attributes; ``--export-events`` still adds ``event_key``.

In both node modes, nodes carry ``tactics`` and ``techniques``, and ``--export-sigma`` rows ``sigma_tactics`` and
``sigma_techniques``: the union of the ATT&CK tags of every matching Sigma rule, separated by a vertical bar. Tactics use
their official ATT&CK name in matrix order (``attack.defense-evasion`` is Stealth); techniques are sorted and also hold
group and software IDs. These values describe what the rules can detect, not the stage of an attack.

Sigma Rules
-----------

ReconGraph uses **Sigma rules** to categorize log entries into high-level security events.
You can download the official rules from the `SigmaHQ repository <https://github.com/SigmaHQ/sigma>`_.

.. note::
   The Sigma rules are released under the `Detection Rule License (DRL) 1.1 <https://github.com/SigmaHQ/Detection-Rule-License>`_.
   See the :doc:`license` page for more details.


Structure
^^^^^^^^^

Rules should be in **YAML (.yml)** format and follow the standard Sigma specification. The tool specifically utilizes:

*   **Logsource**: To filter which rules apply to which type of log (e.g., ``category: webserver``).
*   **Detection**: The selection logic (strings, lists, or dictionaries) used to match log content.
*   **Level**: To assign severity (Critical, High, Medium, Low) to the resulting graph nodes.

Values are Sigma strings and compared case-insensitively, following the Sigma specification (*String Wildcard* and
*Escape Character*) and Hayabusa, read from left to right:

*   ``*`` matches any text (newlines included) and ``?`` exactly one character.
*   ``\*``, ``\?`` and ``\\`` are the character itself; a backslash before any other character is a backslash. So
    ``\\cmd.exe`` and ``\cmd.exe`` are the same value, ``\\\\`` is two backslashes, ``\\*`` is a backslash followed by
    the ``*`` wildcard and ``\\\*`` a backslash followed by an asterisk.
*   This applies to keywords and to plain, ``contains``, ``startswith`` and ``endswith`` values (after ``windash``).
    ``re``, ``cidr``, ``lt``/``lte``/``gt``/``gte``, ``fieldref`` (the other field's value is text) and
    ``base64``/``base64offset`` values are not Sigma strings.

Rule Location
^^^^^^^^^^^^^

When running ReconGraph, you must provide a path to a directory containing these rules. The tool will recursively search for all ``.yml`` files within that directory.

Supported Log Types
--------------------

The tool includes heuristic detection for several common log types to improve Sigma matching:

1.  **Web Logs**: Nginx, Apache, or generic Proxy access logs.
2.  **Authentication Logs**: Linux SSH (`auth.log`) and PAM modules.
3.  **Syslog**: General Linux system logs, including kernel and auditd events.
